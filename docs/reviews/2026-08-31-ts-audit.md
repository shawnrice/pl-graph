## 1. Systemic: prototype-chain lookups (`key in obj`, `obj[userKey]`) — THE headline

A plain object (`{}`) inherits `toString`/`constructor`/`hasOwnProperty`/`valueOf`/…
from `Object.prototype`. `'toString' in {}` is `true` and `({})['toString']` is a
function — with **no** patching, triggered by ordinary user data (a property named
`toString`, a GQL fn `toString`, an MCP algo `constructor`). Two harms: (a) a
**byte-identity break** vs the HashMap-backed Rust engine (which has no inherited
keys); (b) wrong values / mis-dispatch / rollback corruption. Fuzzers miss it (they
never generate reserved-word keys). Fix pattern already exists in-repo
(`executor.ts:284` `propPresent`, `projection.ts:380` `selectStep`, `protocol.ts` `Map`,
`temporal.ts:673`).

- [ ] **[high]** core `Vertex.ts:248` (+`121,158,159,222,230`), `Edge.ts:118` (+`141,176,177,232,240`) — `key in this.properties`: `hasProperty('toString')`→true → byte-identity break **and** rollback corruption (undo restores inherited fn) → `hasOwn`.
- [ ] **[low]** core `Graph.ts:2295,2405,2575,2907` — same in constraint checks (key is a declared-constraint name, lower risk) → `hasOwn`.
- [ ] **[high]** gremlin `dispatch.ts:183,407`; `projection.ts:170,195,261,287,314` — `has`/`values`/`valueMap`/`elementMap` emit inherited fns → `hasOwn` (sibling `selectStep:380` already does).
- [ ] **[med]** gremlin `misc.ts:88-93,225,232` — `math()` `UNARY_FN[name]`/`BINARY_FN[name]`/`MATH_CONSTS[name]` invoke prototype fns instead of faulting → `Object.create(null)`/`hasOwn`.
- [ ] **[high]** gql `scalars.ts:784` `NUM_CONSTANTS` + `759,765,771,713,725` (`UNARY_NUM`/`STR_ARG_POSITIONS`/…) — `RETURN toString(5)` leaks a raw `TypeError` `code:undefined` from the public API (violates LenkeError-code invariant) → build tables with `Object.create(null)`.
- [ ] **[med]** gql `clauses.ts:194` — `_MERGE` key inference `key in properties` on user map → `hasOwn`.
- [ ] **[high]** serialization `csv/index.ts:674` — `!(key in bag)` → encodes `"function Object()…"` for a missing cell → breaks round-trip + byte-identity → `hasOwn`.
- [ ] **[high]** mcp `tools.ts:198` — `ALGORITHMS[name]` invokes prototype fns (schema `enum` not enforced server-side) → `hasOwn` or make `ALGORITHMS` a `Map` (mirrors `protocol.ts`).
- [ ] **[med]** sync `engine.ts:333` — `scopeOf` `!(k in params)` mis-resolves scope to `Object` → `hasOwn`.
- [ ] **[med]** FUZZER GAP — differential/gremlin/codec/write fuzzers never generate reserved-word property keys (`constructor`/`toString`/`__proto__`/`hasOwnProperty`). Add them to the key generator so this class can't regress; re-run `bun run fuzz`.

> NOT bugs (correctly left alone by reviewers): `'from' in element`, `'label' in item`,
> `'hop' in el`, `'id' in v` (internal tagged-union discriminators), and
> `'size' in set` / `'length' in x` (testing an _inherited_ prop — `hasOwn` would be
> wrong there).

- [x] **[med][CONFIRMED]** engine (Rust) lacks the element-name validation the TS `Graph` enforces. ## Engine (Rust) robustness — third pass, 2026-09-01

- [x] **[HIGH][CONFIRMED]** engine `gql.rs` + `gremlin.rs` — the recursive-descent parsers have NO nesting-depth cap (only _traversal_/operator-chain depth is limited, which is post-parse and too late). A plain query string of deeply nested structure overflows the stack and ABORTS the process: `RETURN [[[…1…]]]` at depth ~6000 (~12 KB) → SIGSEGV [verified: exit 139; depth 3000 fine]; also `RETURN ((((1))))`, `NOT NOT … true`, and Gremlin `where(__.where(__.where(…)))`. Uncatchable — parse runs OUTSIDE the `ffi.rs` `guarded` catch_unwind (`ffi.rs:573/604/641`), and a stack overflow isn't recoverable by `catch_unwind` anyway. Native: process abort (DoS for an embedded/server host). wasm: the "unreachable" trap that kills the REPL. The same unbounded recursion is also in the post-parse consumers (`optimize_indexed`, `exec` expr `eval`). Fix: a hard nesting-depth cap in BOTH parsers that rejects with `E_SYNTAX`/`E_RESOURCE_EXHAUSTED` before building the tree; optionally a query-length cap in `ffi.rs` (there is none today).
- [x] **[low][CONFIRMED]** engine `algo.rs` — algorithm CALL/direct config has no cap on `iterations` or `threads`. `{iterations: 1e18}` saturates to `u32::MAX` (~4.29e9) fixed iterations → hang/DoS (not a panic); a huge `threads` asks rayon for that many OS threads (falls back to inline on builder failure, so no fault, but churns first). # Fourth pass — 2026-09-02 (correctness discovery: paths, tx, index-seeding)

Two parallel correctness hunts (index-seeding, transactions) + direct cross-engine
probes of aggregation / strings / temporal / paths / syntax. All below are CONFIRMED
with a repro; in every divergence native is the correct/robust side.

- [x] **[HIGH][CONFIRMED]** native host `transaction()` ABORTS the process when nested. `backend.ts:171` documents "nesting joins the outer frame" and the TS engine does exactly that (inner joins outer; outer rollback discards inner writes). The native path has NO depth tracking: a second `beginTransaction` → `store.begin()` hits `assert!(self.undo.is_none(), "nested transactions are not supported")` (`store.rs:4093`), a non-unwinding panic ACROSS the FFI boundary → `abort()` — an uncatchable whole-process crash [verified: `g.transaction(() => g.transaction(...))` triggers a Bun crash report]. wasm shares the path (REPL-killing "unreachable"). The ISO-keyword path `run_tx_control` guards this gracefully with `E_INVALID_GRAPH_OP`; only the host API is unguarded. Fix: depth-count the host tx (join-outer like TS) or return `E_INVALID_GRAPH_OP` instead of asserting.
- [x] **[med][CONFIRMED]** GQL reserved words can't be dot-accessed as property/field names in the TS engine but can in native. `RETURN n.count` / `n.date` / `n.value` / `n.size` / `n.year` / `n.month` / `n.order` / `n.group` / `n.start` / `n.end` / `n.min` / `n.max` / … (23 common words) → `E_SYNTAX` in `@lenke/gql`, but return the value in native — for a direct property (`n.count`) AND a nested record field (`n.rec.date`). Accept/reject divergence on common property names. TS workaround is backtick-quoting (`` n.`count` ``; `n['count']` is map-indexing and returns null on a node). Native accepts keywords as member names (like JS `obj.count`). Fix: allow a reserved word as the property name after `.` in the TS parser (match native), or decide native should also require delimiting.
- [ ] **[med][CONFIRMED]** `version`/`epoch` diverge on a ROLLED-BACK tx: native advances them by 1 (the forward `touch()`/`bump_epoch` are never reverted by the undo replay), TS leaves them unchanged. Stored values are correct on both (no corruption), but a rolled-back native tx spuriously invalidates every reactive-store subscriber (fingerprint bump) while TS notifies none — relevant to `@lenke/sync` replica invalidation and React `version`/`epoch` subscriptions. Fix: snapshot/restore version+epoch across a rollback, or don't bump until commit.
- [x] **[low][CONFIRMED]** `{0,0}` quantified path returns 1-hop rows in TS. `MATCH (a)-[:R]->{0,0}(b)` must match exactly zero hops (b = start); native returns only the start, TS returns start + 1-hop neighbours (as if `{0,1}`). Root cause: `matching.ts:1134` emit condition checks only the lower bound (`rep2 >= min`), never the upper — the unconditionally-generated first hop slips through when `max=0`. Fix: `&& (top.max === null || rep2 <= top.max)`.
- [ ] **[low-med][CONFIRMED]** schema DDL (createIndex / createUniqueConstraint / …) run INSIDE a tx that then ABORTS persists — the tx's data writes revert but its schema op does not (verified: the index survives + the constraint still enforces). Holds identically on BOTH engines (DDL implicit-commit), so not a divergence, but undocumented rollback residue / a footgun. Fix: transaction-log schema ops, or document the split.
